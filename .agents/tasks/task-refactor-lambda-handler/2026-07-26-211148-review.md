# Domain-split of monolithic Lambda into four handlers

The 1538-line monolithic handler was decomposed into four domain-specific Lambda functions (recipes, ingredients-on-hand, supermarkets, sort-ingredients) with shared utilities extracted to a `shared/` module. The CDK stack was updated to deploy four separate `NodejsFunction` constructs with route-level API Gateway integrations and scoped IAM permissions. The split follows domain boundaries cleanly: each handler owns its CRUD surface and the shared module provides DynamoDB client, Bedrock client, CORS response helper, and auth extraction.

**Watch for:** sort-ingredients Lambda is over-permissioned (DynamoDB grant + TABLE_NAME env var it never uses) [confirmed]; the `shared/bedrock.ts` module instantiates a Bedrock client at module load in handlers that never call Bedrock (ingredients-on-hand, supermarkets) since it's in the barrel export, causing an unnecessary SDK initialization on cold start [confirmed]; duplicate AI response-parsing logic across sort-ingredients functions is carried over from the monolith but could have been consolidated during the refactor [confirmed].

## High-level view

The decomposition strategy is one handler per domain, a shared utilities layer, and per-route CDK integrations that map each API Gateway resource to its owning Lambda. IAM permissions are scoped so that only the two AI-calling handlers (recipes, sort-ingredients) get Bedrock access, though the DynamoDB grant is applied uniformly to all four regardless of need.

The shared module uses barrel exports, which means every handler that imports from `../shared` triggers module-level initialization of both the DynamoDB and Bedrock clients. For the sort-ingredients handler, which doesn't touch DynamoDB, this means `DynamoDBDocumentClient.from(...)` runs on cold start for no reason. For ingredients-on-hand and supermarkets, which don't touch Bedrock, `BedrockRuntimeClient` is constructed unnecessarily.

The sort-ingredients handler authenticates the user (returns 401 without a valid `sub` claim) but then discards the userId entirely — none of its three routes query or write user-scoped data. This preserves the original behavior where auth was checked once at the top of the monolith before routing, so it's not a regression, but it means the handler pays for an auth contract it doesn't enforce meaningfully.

## Over-permissioning of the sort-ingredients Lambda

The CDK stack grants all four handlers identical DynamoDB read/write access and passes `TABLE_NAME` in their environment:

```typescript
recipesTable.grantReadWriteData(sortIngredientsHandler);
```

But `sort-ingredients.ts` imports only `bedrockClient`, `response`, and `getUserId` from shared — it never references `docClient` or `TABLE_NAME`. It performs no DynamoDB operations. The grant widens the blast radius if the handler is compromised. Since the barrel import still causes a `DynamoDBDocumentClient` to be instantiated at module load, the unused permission is technically reachable through the module-scoped variable, making the least-privilege violation slightly more than cosmetic.

## Barrel export coupling and cold-start initialization

`shared/index.ts` re-exports everything:

```typescript
export { docClient, TABLE_NAME } from './db';
export { bedrockClient } from './bedrock';
export { corsHeaders, response } from './response';
export { getUserId } from './auth';
```

When any handler writes `import { response, getUserId } from '../shared'`, the JS runtime still evaluates `db.ts` and `bedrock.ts` at the top level because they're part of the same barrel. That means:

- `ingredients-on-hand.ts` and `supermarkets.ts` instantiate a `BedrockRuntimeClient` they never call.
- `sort-ingredients.ts` instantiates a `DynamoDBDocumentClient` it never uses.

The SDK client constructors have side effects (they set up internal state, read env vars), so esbuild won't tree-shake them. The practical cold-start cost is small (a few ms per unused client), but it makes the dependency graph misleading and compounds the over-permissioning issue above — if the barrel always pulls in `docClient`, then every handler has a live reference to DynamoDB whether it needs one or not.

## Duplicated Bedrock response parsing in sort-ingredients

`sortIngredients` and `sortIngredientsManual` contain identical logic for stripping markdown code fences from model output, parsing the resulting JSON, normalizing between `{groups: [...]}` wrapper and bare array formats, and matching product names/indices back to the original ingredient list using fuzzy string matching. This is roughly 30 lines duplicated verbatim. Extracting a `parseAndMatchGroups(outputText: string, ingredients: Ingredient[])` helper would ensure future bug fixes to the fuzzy matching logic apply uniformly to both code paths.

## Dead OPTIONS handling in all handlers

The `defaultCorsPreflightOptions` on the RestApi means API Gateway intercepts and responds to OPTIONS requests before they reach Lambda. The per-handler `if (event.httpMethod === 'OPTIONS') return response(204)` check is unreachable in production. This is defensive code carried over from the monolith — not a problem, but worth knowing when reasoning about CORS behavior during debugging.
