# DynamoDB production seed for PR preview stacks

This change adds a workflow step that copies all items from the production DynamoDB table into the ephemeral PR stack's table after CDK deploys it. It exposes the table name via a new `CfnOutput` on the CDK stack so both the prod and PR table names can be read from CloudFormation at deploy time. The script paginates through the production table with `aws dynamodb scan`, batches items into groups of 25, and writes them with `batch-write-item`.

**Watch for:** Unprocessed items from `batch-write-item` are silently dropped (confirmed). The pagination token field is wrong for raw `dynamodb scan` — the CLI uses `LastEvaluatedKey`/`--exclusive-start-key`, not `NextToken`/`--starting-token` (confirmed). The script exposes production data (including PII) to anyone with access to the PR environment (likely).

## High-level view

The seeding script has a structural pagination bug. The AWS CLI's `dynamodb scan` returns `LastEvaluatedKey` (a DynamoDB-native key object) to indicate more pages, and expects `--exclusive-start-key` to resume. The script looks for `.NextToken` (an AWS CLI higher-level pagination token used with `--starting-token`) which only works when the CLI's built-in paginator is in use — but `scan` with `--output json` returns the raw DynamoDB response shape. The script will silently stop after the first 1 MB page if the table is larger than that.

The `batch-write-item` call ignores its response entirely. DynamoDB returns `UnprocessedItems` when it throttles or partially fails a batch. Without retry logic, items are silently lost from the seed. For a test-data seeding use case this may be tolerable, but it means the PR environment's data could be an incomplete subset of production with no indication that anything went wrong.

Copying full production data into a PR environment with no filtering means any PII, credentials, or sensitive content in the table is now accessible to anyone who can reach the PR stack. Whether this matters depends on what's stored and who has access to PR deployments.

<summary>Issues (4)</summary>

1. **Pagination uses wrong token mechanism** — `dynamodb scan` returns `LastEvaluatedKey` and expects `--exclusive-start-key` to continue. The script reads `.NextToken` and passes `--starting-token`, which won't paginate. Replace with `--exclusive-start-key` and read `.LastEvaluatedKey` from the JSON response.
2. **UnprocessedItems silently dropped** — `batch-write-item` can return unprocessed items on throttling. The response is piped to `/dev/null`. Add a retry loop or at minimum fail the step if `UnprocessedItems` is non-empty.
3. **Production data exposure** — Full production table contents (potentially including PII) are copied into PR environments accessible to PR reviewers. Consider filtering to a safe subset or using synthetic data.
4. **BATCH_SIZE jq expression has unnecessary nesting** — The `'[.[$start:$end]] | .[0] | length'` wraps the slice in an extra array then unwraps it; should be `'.[$start:$end] | length'`. This doesn't cause incorrect behavior but makes the intent unclear.

## Pagination is broken for tables beyond one page

The `aws dynamodb scan` API returns a `LastEvaluatedKey` field (a DynamoDB key map like `{"userId": {"S": "abc"}, "id": {"S": "123"}}`) when there are more items to fetch. The caller passes that back as `--exclusive-start-key`. The script instead reads `.NextToken` from the JSON output and passes `--starting-token`:

```bash
NEXT_TOKEN=$(echo "$SCAN_OUTPUT" | jq -r '.NextToken // empty')
# ...
aws dynamodb scan --table-name "$PROD_TABLE" --starting-token "$NEXT_TOKEN"
```

`--starting-token` is a feature of the AWS CLI's client-side paginator (used with commands like `aws dynamodb scan --page-size ...` or higher-level commands like `list-tables`). When `scan` is called directly and returns raw JSON, the pagination key is `LastEvaluatedKey` and the resume parameter is `--exclusive-start-key`, which takes a JSON key map, not a string token.

The result: for any production table larger than 1 MB (the scan page limit), the loop exits after the first page because `.NextToken` is always empty. The script reports success with a partial copy. (confirmed)

The fix is:

```bash
LAST_KEY=$(echo "$SCAN_OUTPUT" | jq -c '.LastEvaluatedKey // empty')
if [[ -z "$LAST_KEY" || "$LAST_KEY" == "null" ]]; then
  break
fi
# next iteration:
aws dynamodb scan --table-name "$PROD_TABLE" --exclusive-start-key "$LAST_KEY" --output json
```

## batch-write-item drops throttled items silently

`aws dynamodb batch-write-item` responds with an `UnprocessedItems` map when DynamoDB cannot process all items in a batch (most commonly due to provisioned throughput throttling or table-level rate limits). The script discards this response:

```bash
aws dynamodb batch-write-item --request-items "$BATCH_PAYLOAD" --output json > /dev/null
```

If the PR table is freshly created and still in the "burst capacity" phase, small batches will likely succeed. But if the production table has hundreds of items, later batches may be throttled, and those items are permanently lost from the seed with no error. (confirmed — response is discarded, no retry)

A minimal fix: capture the response, check `.UnprocessedItems | length`, and either retry with exponential backoff or fail the step so the user knows the seed was incomplete.

## Production data in PR environments

The script performs a full, unfiltered scan of the production table. If the recipes table stores user-generated content, email addresses, or any PII tied to the `userId` partition key, that data now lives in an ephemeral stack that may have weaker access controls than production. The PR stack shares the same AWS account and the same Cognito user pool (as shown by the `mainUserPoolId` context pass-through), so in principle the same users have access — but the blast radius changes if PR stacks have broader IAM policies or if PR URLs are shared publicly. (likely concern — depends on data sensitivity)

## Minor: BATCH_SIZE jq expression

```bash
BATCH_SIZE=$(echo "$ITEMS" | jq --argjson start "$BATCH_START" --argjson end "$BATCH_END" \
  '[.[$start:$end]] | .[0] | length')
```

The wrapping in `[...]` and then indexing `.[0]` is a no-op — `.[$start:$end]` already produces an array. This should be `.[$start:$end] | length`. (confirmed — cosmetic)
